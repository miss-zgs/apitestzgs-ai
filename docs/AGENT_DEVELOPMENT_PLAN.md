# API 测试 Agent 开发详细方案（小白版）

> 本方案基于现有 `apitestzgs` API 测试框架，设计一个 AI Agent 系统，使其能通过自然语言驱动自动化测试。
> 面向零基础开发者，涵盖：概念科普、架构设计、技术选型、代码结构、开发步骤、注意事项、安全规范等所有方面。

---

## 一、基础概念科普（先搞懂这些再动手）

### 1.1 什么是 Agent？

**一句话定义**：Agent 是一个能自主决策"下一步做什么"的 AI 程序。

**和普通程序的区别**：

| 维度 | 普通程序 | Agent |
|------|---------|-------|
| 执行方式 | 按写死的代码一步步执行 | 根据目标自主规划步骤 |
| 遇到问题 | 报错退出 | 分析原因，换个方法重试 |
| 输入方式 | 固定参数 | 自然语言描述 |
| 灵活性 | 只能做预设的事 | 能应对未预见的场景 |

### 1.2 Agent 的四个核心组件

```
┌─────────────────────────────────────────────┐
│                 Agent 系统                    │
│                                              │
│  🧠 LLM（大语言模型）— 负责思考和决策          │
│  📋 Prompt（系统指令）— 定义 Agent 的角色和规则 │
│  🔧 Tools（工具集）— Agent 能做的具体操作       │
│  💾 Memory（记忆）— 记住历史信息和上下文        │
│                                              │
└─────────────────────────────────────────────┘
```

**详细说明**：

| 组件 | 作用 | 类比 | 注意事项 |
|------|------|------|----------|
| **LLM** | 理解任务、做推理决策 | 人的大脑 | 选择稳定的模型，注意 token 成本 |
| **Prompt** | 告诉 LLM 它是谁、能做什么、不能做什么 | 岗位说明书 | 是 Agent 质量的关键，需反复调优 |
| **Tools** | 执行具体操作（发请求、读文件、做断言） | 人的手脚 | 描述必须精确，否则 Agent 不知道何时用 |
| **Memory** | 保存对话历史、执行结果 | 记事本 | 需要控制大小，太长会超 token 限制 |

### 1.3 Agent 的工作循环（ReAct 模式）

```
任务输入
   ↓
┌─────────────────────────────┐
│  Thought（思考）：我应该做什么？ │
│       ↓                      │
│  Action（行动）：调用某个工具   │
│       ↓                      │
│  Observation（观察）：看到结果  │
│       ↓                      │
│  是否完成？                    │
│    ├─ 否 → 回到 Thought       │
│    └─ 是 → 输出最终结果        │
└─────────────────────────────┘
```

**注意事项**：
- 每一轮循环都会消耗 LLM 的 API 调用（= 花钱）
- 一般限制最大循环次数（如 10 次），防止死循环
- 需要设计"兜底策略"：循环到上限仍未完成时怎么办

### 1.4 关键术语表

| 术语 | 解释 | 例子 |
|------|------|------|
| **Token** | LLM 处理的最小文本单位 | "Hello" ≈ 1 token，一个汉字 ≈ 1-2 token |
| **Prompt Engineering** | 设计 LLM 输入的技巧 | 给 Agent 写系统指令 |
| **Tool Calling** | LLM 决定调用哪个工具 | "我需要发一个 GET 请求" → 调用 http_client |
| **Function Schema** | 工具的"说明书"（参数、返回值） | JSON 格式描述工具怎么用 |
| **RAG** | 检索增强生成 | 让 Agent 先搜索知识库再回答 |
| **Hallucination** | 幻觉，LLM 编造不存在的信息 | 编造接口地址、伪造响应 |
| **Chain of Thought** | 思维链，让 LLM 分步推理 | "先分析→再执行→最后验证" |

                          ↕ 自然语言

│                     Agent 核心层                       │

│  ┌─────────┐  ┌──────────┐  ┌─────────┐  ┌────────┐ │
│  │ Planner │  │ Executor │  │ Checker │  │ Memory │ │

                          ↕ 工具调用

### 2.2 各层职责说明

| 层 | 职责 | 注意事项 |
|----|------|----------|
| **用户层** | 接收自然语言输入，展示执行结果 | 先做 CLI，稳定后再做 Web |
| **Agent 核心层** | 理解任务→规划步骤→执行→验证 | 核心逻辑所在，需要稳定可靠 |
| **工具层** | 执行具体操作 | 直接复用现有模块，无需重写 |
| **数据层** | 配置、用例、日志、报告 | 保持现有目录结构不变 |

### 2.3 运行时序图

```
用户: "测试登录接口，验证正确密码和错误密码两种情况"
  │
  ▼
Agent [Planner]: 分析需求，拆解为 2 个测试场景
  │
  ▼
Agent [Executor]: 
  ├── 场景1: 正确密码
  │   ├── 调用 http_client.post("/api/login", json={"user":"admin","pwd":"123"})
  │   ├── 调用 assertion.assert_status_code(response, 200)
  │   └── 调用 assertion.assert_json_field(response, "$.data.token", not_empty)
  │
  ├── 场景2: 错误密码
  │   ├── 调用 http_client.post("/api/login", json={"user":"admin","pwd":"wrong"})
  │   ├── 调用 assertion.assert_status_code(response, 401)
  │   └── 调用 assertion.assert_json_field(response, "$.message", "密码错误")
  │
  ▼
Agent [Checker]: 汇总结果
  │
  ▼
输出: "✅ 场景1通过 ✅ 场景2通过，登录接口测试全部通过"
```

## 三、技术选型

### 3.1 核心技术栈

| 组件 | 选型 | 理由 | 备选方案 |
|------|------|------|----------|
| **编程语言** | Python 3.9+ | 和现有框架一致 | — |
| **LLM** | 通义千问 qwen-max | 阿里内部直接调用，免费/低成本 | GPT-4、Claude |
| **Agent 框架** | LangChain | 最成熟，文档丰富，适合小白 | CrewAI、AutoGen |
| **工具封装** | LangChain Tools | 标准格式，易对接 | 自己写 Function Calling |
| **记忆管理** | ConversationBufferWindowMemory | 保留最近 N 轮对话 | Redis 持久化 |
| **入口交互** | 命令行（初期） | 最简单最快 | 后期可加 Web/钉钉 |

### 3.2 依赖包清单

```
# Agent 相关（新增）
langchain>=0.2.0
langchain-community>=0.2.0
dashscope>=1.20.0          # 通义千问 SDK
pydantic>=2.0.0            # 数据校验

# 已有（保持不变）

PyYAML>=6.0.1
jsonpath-ng>=1.6.0
python-dotenv>=1.0.0
```

### 3.3 选型注意事项

| 要点 | 说明 |
|------|------|
| **LLM 的选择** | 优先选同网络环境能直接调用的（阿里内部用通义千问）；外网项目可用 GPT-4 |
| **框架的选择** | LangChain 虽然有些"重"，但文档最全、社区最大，小白学习资源多 |
| **版本锁定** | LangChain 更新很快，一定要锁版本号，否则升级可能 break |
| **本地 vs 云端** | 初期全用云端 LLM API；后期如果对延迟/隐私有要求再考虑本地模型 |

## 五、核心模块详细设计

### 5.1 Prompt 设计（最关键的部分）

#### 5.1.1 System Prompt

```
你是一名专业的 API 接口测试工程师，服务于飞猪业务。

【你的能力】
1. 根据自然语言需求，设计接口测试方案
2. 使用工具发送 HTTP 请求
3. 对响应结果进行断言验证
4. 分析测试失败的原因并给出修复建议
5. 处理接口间的依赖关系（如：登录获取 token → 带 token 查询）

【你的工作流程】
1. 理解用户的测试需求
2. 确认需要测试的接口地址、参数、预期结果
3. 逐步执行测试（先正向后异常）
4. 汇总测试结果

【你的约束】
- 所有接口地址必须从用户提供或数据文件中获取，禁止编造
- 如果信息不足，必须先向用户确认，不能猜测
- 每次请求都必须检查状态码
- 遇到 5xx 错误时提醒用户可能是服务端问题
- 单次任务最多执行 10 个请求，超过需要确认

【响应格式】
- 每个测试步骤用 ✅/❌ 标记结果
- 失败时附上详细的错误信息和可能原因
- 最后给出整体测试结论
```

#### 5.1.2 Prompt 设计注意事项

| 要点 | 说明 | 后果（如果忽视） |
|------|------|----------------|
| **角色定义要具体** | 不是"你是助手"而是"你是 API 测试工程师" | Agent 回答飘忽不定，不专业 |
| **能力边界要明确** | 列出能做什么、不能做什么 | Agent 乱用工具或编造信息 |
| **流程要规定** | 先做什么后做什么 | Agent 跳步骤，遗漏关键验证 |
| **约束要严格** | "禁止编造 URL"这类硬规则 | 幻觉问题，测试结果不可信 |
| **输出格式要统一** | 定义结果的展示方式 | 输出混乱，难以解读 |
| **兜底要设计** | 信息不足时怎么办 | Agent 瞎猜参数导致误判 |

#### 5.1.3 Prompt 迭代流程

```
V1: 写初版 Prompt → 测试 5-10 个场景 → 记录问题
V2: 针对问题加约束/改措辞 → 再测试 → 再记录
V3: 反复迭代 3-5 轮后趋于稳定
     │
     └── 建议：每次改动只改一处，A/B 对比效果
```

### 5.2 工具（Tools）设计

#### 5.2.1 工具设计原则

| 原则 | 说明 | 例子 |
|------|------|------|
| **单一职责** | 每个工具只做一件事 | ❌ "发请求并断言" → ✅ "发请求" + "做断言" |
| **描述精确** | 工具描述决定 Agent 何时选用 | "发送 HTTP GET/POST 请求并返回响应" |
| **参数明确** | 必选/可选要标清，类型要标 | `url: str (必填)`, `headers: dict (选填)` |
| **返回值可读** | 返回结果要让 LLM 能理解 | 返回格式化的字符串而非原始对象 |
| **错误友好** | 出错时返回有用的错误信息 | "请求超时(30s)，URL: xxx，建议检查网络" |
| **幂等安全** | 读操作随便调，写操作要确认 | GET 安全，POST/DELETE 需要二次确认 |

#### 5.2.2 工具清单设计

| 工具名 | 功能 | 输入参数 | 输出 | 安全等级 |
|--------|------|----------|------|----------|
| `send_http_request` | 发 HTTP 请求 | method, url, headers, params, body | 状态码+响应体 | ⚠️ 中 |
| `check_status_code` | 校验状态码 | response, expected_code | 通过/失败+详情 | ✅ 安全 |
| `check_json_field` | jsonpath 断言 | response, path, expected | 通过/失败+详情 | ✅ 安全 |
| `load_test_data` | 加载用例数据 | file_path | 用例列表 | ✅ 安全 |
| `read_file` | 读取文件内容 | path | 文件内容 | ✅ 安全 |
| `save_test_result` | 保存测试结果 | results | 保存路径 | ⚠️ 中 |
| `report_bug` | 记录缺陷 | title, detail | 记录结果 | ⚠️ 中 |

#### 5.2.3 工具描述模板（Function Schema）

```python
{
    "name": "send_http_request",
    "description": "向指定 URL 发送 HTTP 请求。支持 GET/POST/PUT/DELETE/PATCH 方法。返回 HTTP 状态码和响应体（JSON 或文本）。如果请求失败会自动重试 3 次。",
    "parameters": {
        "type": "object",
        "properties": {
            "method": {
                "type": "string",
                "enum": ["GET", "POST", "PUT", "DELETE", "PATCH"],
                "description": "HTTP 方法"
            },
            "url": {
                "type": "string",
                "description": "请求 URL，可以是完整 URL 或相对路径（会自动拼接 base_url）"
            },
            "headers": {
                "type": "object",
                "description": "请求头，键值对格式。如需认证可传 Authorization"
            },
            "params": {
                "type": "object",
                "description": "URL 查询参数"
            },
            "json_body": {
                "type": "object",
                "description": "请求体（JSON 格式），仅 POST/PUT/PATCH 时使用"
            }
        },
        "required": ["method", "url"]
    }
}
```

#### 5.2.4 工具开发注意事项

| 要点 | 详细说明 |
|------|---------|
| **返回值要字符串化** | LLM 只能处理文本，不能传 Python 对象。响应体太长要截断 |
| **响应体截断** | 超过 2000 字符时只返回前 2000 字符 + "...已截断"，防止超 token |
| **敏感信息脱敏** | 返回中如有密码/密钥，需要用 *** 遮掩 |
| **超时处理** | 给每个工具设超时时间，防止 Agent 卡住 |
| **并发控制** | 初期串行执行，不要并发，避免复杂性 |
| **日志记录** | 每次工具调用都写日志，方便排查 |

### 5.3 记忆（Memory）设计

#### 5.3.1 记忆类型

| 类型 | 内容 | 生命周期 | 存储方式 |
|------|------|---------|---------|
| **短期记忆** | 当前对话的历史消息 | 单次会话 | 内存 |
| **工作记忆** | 当前任务的中间结果（如 token） | 单次任务 | context 变量 |
| **长期记忆** | 历史测试用例、接口文档、经验总结 | 永久 | 本地文件/向量库 |

#### 5.3.2 记忆管理策略

```
短期记忆（对话历史）:
├── 保留最近 10 轮对话
├── 超过时总结前面的内容为摘要
└── 每轮保存: {role, content, tool_calls, tool_results}

工作记忆（任务上下文）:
├── 复用现有的 utils/context.py
├── 存储变量：token, user_id, order_id 等
└── 每个任务开始时清空

长期记忆（知识库）:
├── 接口文档：data/ 目录下的 YAML 文件
├── 历史用例：之前执行成功的用例
└── 经验库：失败原因分析记录
```

#### 5.3.3 注意事项

| 要点 | 说明 |
|------|------|
| **Token 预算** | LLM 有上下文长度限制（如 8K/32K/128K），记忆太多会超限 |
| **信息压缩** | 响应体太长不能全存，只存关键字段 |
| **隐私安全** | 密码/密钥不能存入长期记忆 |
| **记忆污染** | 错误的记忆会误导后续决策，需要清除机制 |

### 5.4 安全边界设计

#### 5.4.1 权限分级

```
Level 0 - 只读（初期默认）:
├── ✅ 读取配置文件
├── ✅ 读取测试数据
├── ✅ 查看日志
└── ❌ 修改任何文件

Level 1 - 可执行测试:
├── ✅ 发送 HTTP 请求（仅测试环境）
├── ✅ 执行断言
├── ✅ 生成测试报告
└── ❌ 修改代码/配置

Level 2 - 可写数据:
├── ✅ 生成新的测试用例文件
├── ✅ 记录 Bug 到 BUGFIX.md
├── ✅ 保存测试结果
└── ❌ 修改框架代码

Level 3 - 完全自主（需人工审批）:
├── ✅ 修改框架代码
├── ✅ 安装依赖
├── ✅ 修改配置
└── ⚠️ 每次操作需人工确认
```

#### 5.4.2 安全规则清单

| 规则 | 具体要求 | 实现方式 |
|------|---------|---------|
| **环境隔离** | Agent 只能调用测试环境接口 | 工具层强制校验 URL 前缀 |
| **请求限流** | 单次任务最多 30 个请求 | 工具层计数器 |
| **数据脱敏** | 日志中遮掩密码/密钥 | 日志过滤器 |
| **操作确认** | 写操作（POST/PUT/DELETE）前确认 | 工具层拦截 |
| **成本控制** | 单次任务最多消耗 10000 token | Agent 层计数器 |
| **超时熔断** | 单个工具调用超时 30s 自动终止 | 工具层超时包装 |
| **错误重试上限** | 同一操作最多重试 3 次 | Agent 层计数器 |

## 七、开发规范

### 7.1 代码规范

| 规范 | 要求 | 原因 |
|------|------|------|
| **命名** | 见名知义，禁止缩写 | Agent 代码需要频繁阅读和调试 |
| **类型标注** | 所有函数必须有类型标注 | 方便 IDE 提示和错误检查 |
| **文档字符串** | 每个函数/类必须有 docstring | Agent 工具描述需要参考 |
| **异常处理** | 所有工具函数必须 try-except | 不能让 Agent 因异常中断 |
| **日志记录** | 关键操作必须有日志 | 排查 Agent 行为的唯一手段 |
| **配置外置** | 不硬编码任何配置 | 方便切环境 |

### 7.2 Prompt 管理规范

| 规范 | 要求 |
|------|------|
| **版本管理** | 每次修改 Prompt 都要记录版本号和改动原因 |
| **A/B 测试** | 改 Prompt 后用相同输入对比新旧版本效果 |
| **变量分离** | Prompt 中的动态部分用模板变量，不要硬编码 |
| **长度控制** | System Prompt 不超过 2000 字，太长反而降低效果 |
| **负面约束** | "不要做 X" 比 "做 Y" 更有效，关键约束用否定句 |

### 7.3 测试规范

| 类型 | 覆盖范围 | 执行频率 |
|------|---------|---------|
| **工具单测** | 每个 Tool 函数的输入输出 | 每次修改后 |
| **Prompt 回归** | 固定 10 个场景验证 Agent 行为 | 每次改 Prompt 后 |
| **集成测试** | 完整的用户→Agent→执行→结果流程 | 每周一次 |
| **压力测试** | 100 轮对话的稳定性 | 上线前 |

### 7.4 日志规范

```python
# Agent 日志格式
[2026-06-01 17:00:00] [AGENT] [Task-001] [Thought] 我需要先发送一个 GET 请求
[2026-06-01 17:00:01] [AGENT] [Task-001] [Action] send_http_request(method=GET, url=/api/user/1)
[2026-06-01 17:00:02] [AGENT] [Task-001] [Observation] 状态码: 200, 响应: {"code": 0, ...}
[2026-06-01 17:00:02] [AGENT] [Task-001] [Thought] 请求成功，现在需要验证返回值
```

| 要求 | 说明 |
|------|------|
| 每轮循环必须记录 Thought/Action/Observation | 方便还原 Agent 决策过程 |
| 工具调用必须记录入参和出参 | 排查工具是否被正确使用 |
| Token 消耗必须记录 | 成本监控 |
| 异常必须记录完整 traceback | 排查错误 |

## 八、常见问题和应对方案（避坑指南）

### 8.1 LLM 相关问题

| 问题 | 表现 | 解决方案 |
|------|------|---------|
| **幻觉** | Agent 编造不存在的接口地址 | Prompt 强制约束 + 工具层校验 URL 白名单 |
| **遗忘** | 对话太长后忘记前面说的 | 用滑动窗口 + 关键信息摘要 |
| **拒绝** | LLM 说"我不能执行这个操作" | 调整 Prompt 的角色描述 |
| **格式错误** | 输出的 JSON 格式不对 | Prompt 里给 few-shot 示例 |
| **无限循环** | 一直重复相同操作 | 设置最大循环次数 + 相同操作检测 |
| **选错工具** | 应该做断言却去发请求 | 优化工具描述，加 few-shot 示例 |

### 8.2 工具相关问题

| 问题 | 表现 | 解决方案 |
|------|------|---------|
| **参数缺失** | Agent 调工具时漏参数 | 工具层做默认值处理 + 友好报错 |
| **参数类型错误** | 传了字符串应该传数字 | 工具层自动类型转换 |
| **超时** | 接口响应太慢 Agent 卡住 | 工具层包装超时机制 |
| **权限不足** | 调了不该调的接口 | URL 白名单 + 环境检查 |

### 8.3 工程相关问题

| 问题 | 表现 | 解决方案 |
|------|------|---------|
| **成本失控** | API 调用费用暴增 | 设置 token 上限 + 日报监控 |
| **版本冲突** | LangChain 升级后不兼容 | 锁死版本号 + 升级前先在分支验证 |
| **并发问题** | 多人同时用导致上下文混乱 | 每个会话独立的 context 实例 |
| **数据泄露** | API Key 被提交到仓库 | .gitignore + pre-commit hook 检查 |
